The problem

The core failure

A generated deck is beautiful and dead on arrival.

You can't fix a typo without going back to the model. So nobody uses it twice.

02 · Architecture

One runtime.
Many decks.

The navigation, overview, edit mode and export live in a fixed runtime.js that ships with the skill. Claude never rewrites it.

Every generated deck is therefore just semantic markup plus a theme file — small to produce, cheap to revise, identical in behaviour.

Editing

05 · Try it now — press E

What edit mode gives you

  • Every heading, paragraph and list item becomes directly editable in place.
  • Click any image slot to swap the picture. Drag a file onto it works too.
  • Paste an image with ⌘V and it drops onto the slide — drag to move, scroll to resize.
  • Leave a note on a slide and the next Claude pass reads it as a change request.

06 · Persistence

Saving without base64.

A browser file picker can't hand you a real path, so the usual answer is inlining every image as base64 — a 2 MB photo becomes 2.7 MB of text.

Instead the runtime asks for the deck's folder once via the File System Access API, writes new images into images/, and keeps the markup pointing at relative paths.

fallback: standalone download, images inlined

Anatomy

All the model has to emit

07 · Export

Print to PDF, and the pixels survive.

Chrome → Print → margins None, background graphics on. One slide per landscape page, fonts and gradients intact.

The deck you can't edit is a screenshot with extra steps.

08 · Scope

What ships in v1

  • Layout library, three themes, and a documented markup contract for the model.
  • In-browser editing with save-back to the deck folder.
  • PDF via print stylesheet — no html2canvas, no font mangling.
  • Folder ingestion: point the skill at a directory and it lays out the images it finds.
